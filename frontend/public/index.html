Commerce workflow & Saga compensation

Order creation calls Inventory, reserves stock through gRPC, then saves the order. The existing checkbox simulates a failure after stock reservation so the Order Service asks Inventory to restore it.

The engineering problem

A local Inventory commit can succeed even when a later Order step fails. One database rollback cannot undo a completed operation in another service.

The current solution

The Order Service coordinates the steps and calls the Inventory compensation operation after the simulated failure.

Technical details

Browser → Kong → Order Service → Inventory REST and gRPC. Successful order creation publishes the existing OrderCreated event.

Resilience & Fault ToleranceChallenge J / K · Solutions J1 / K2

Timeouts & circuit breaker

A protected request travels through the Resilience Lab Service to its target. Use the slow response to exercise the existing three-second timeout.

The engineering problem

Calls to a slow or unavailable dependency can pile up. A timeout limits waiting; it does not prove that the remote operation did not finish.

The current solution

After repeated failures, the circuit breaker opens and rejects calls quickly. After its reset delay, it allows a recovery probe.

Experiment controls

Technical details

The existing breaker uses a 3-second timeout, 50% error threshold, volume threshold of 3, and a 15-second reset timeout.

Resilience & Fault ToleranceSolution J2

Retry with exponential backoff & jitter

The target intentionally returns temporary HTTP 503 responses for the first two attempts and succeeds on the third.

The engineering problem

An immediate retry can increase pressure on a dependency that is already struggling. Permanent errors should not be retried.

The current solution

The existing experiment makes at most three attempts, waits longer after each temporary failure, and adds random jitter.

Experiment controls

Technical details

The implementation waits 200–300 ms before retry two and 400–500 ms before retry three. It is a bounded learning experiment, not a retry-budget implementation.

Resilience & Fault ToleranceChallenge L → Solution L

Bounded concurrency with a bulkhead

Five requests arrive at once. The existing Resilience Lab admits two downstream calls while rejecting the remaining three promptly.

The engineering problem

Unbounded work waiting on one slow dependency can consume capacity that healthy traffic needs.

The current solution

A fixed concurrency limit contains the work in this Lab Service instance and reports excess requests as HTTP 503.

Experiment controls

Technical details

This is an in-memory limit of two concurrent target calls in one Lab Service instance. It illustrates bounded concurrency; it is not a cluster-wide resource pool.
